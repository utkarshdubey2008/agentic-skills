# Frontend Excellence

## Overview

Build user interfaces that look, feel, and behave like they were made by a design-aware engineer at a quality company — not generated by an AI. This means real design system adherence, every component state handled, human copy, accessible markup, and no generic AI aesthetic. "It works" is not the bar. "A quality-conscious user would not notice anything wrong" is the bar.

## When to Use

- Building new UI components, pages, or flows
- Reviewing UI before it is shown to users or stakeholders
- Auditing an existing interface for quality gaps
- Implementing designs from a Figma file or spec
- Any time the output will be judged visually, not just functionally

**When NOT to use:** Pure backend work, CLI tooling, or data pipelines with no visual surface.

## Design System Adherence

### Avoid the AI Aesthetic

AI-generated UI has recognizable patterns. Avoid all of them:

| AI Default | Why It Is a Problem | Fix |
|---|---|---|
| Purple/indigo on everything | Models default to "safe" palettes — every app looks identical | Use the project's actual color tokens |
| Excessive gradients | Clash with most design systems and add visual noise | Flat or subtle per the design system |
| rounded-2xl on everything | Maximum rounding ignores the corner radius hierarchy in real designs | Consistent radius from the design system |
| Oversized padding everywhere | Equal generous padding destroys visual hierarchy | Use the spacing scale |
| Shadow on every card | Competing depth slows rendering on low-end devices | Subtle or no shadows unless specified |
| Generic hero + feature card grid | Layout shortcut with no connection to actual content | Content-first layout |
| Bullet lists of three parallel items | Instantly recognizable as AI output | Write actual sentences |
| ✨🎉 emoji on AI features / success | Signals the UI was not thought about | Plain text or a purpose-built icon |

### Spacing

Use the scale. Never invent values:

```css
/* Good — on the 4px scale */
padding: 8px 16px;
gap: 12px;
margin-top: 24px;

/* Bad — invented */
padding: 11px 14px;
gap: 13px;
margin-top: 22px;
```

### Typography

```
h1 → One per page. Page-level intent.
h2 → Section headings.
h3 → Subsections. Used sparingly.
body → 16px minimum on screen.
label/caption → 12–14px minimum.
```

Never use heading elements for visual sizing. `<h3>` because "it looks right" is wrong — use a heading because it is a heading.

### Color

- Use semantic tokens: `--color-primary`, `--color-surface`, `--color-text-muted` — never raw hex in components
- Contrast: 4.5:1 for body text, 3:1 for large text and UI elements
- Never use color as the only signal:

```html
<!-- Bad: color only -->
<span class="text-red-500">Required</span>

<!-- Good: color + icon + text -->
<span class="text-red-500 flex items-center gap-1">
  <ErrorIcon aria-hidden="true" /> Required field
</span>
```

## Component Architecture

### Right Size

```
Too small:  <Label /> with no props — indirection with no abstraction value
Too large:  <UserDashboard /> owning layout, data, auth, and rendering
Right:      <UserCard /> renders one user with a clear, stable prop interface
```

Split a component when it has more than one reason to change, fetches and renders, has 6+ props, or exceeds ~150 lines.

### Composition over Configuration

```tsx
// Bad: prop explosion
<Modal
  title="Confirm Delete"
  confirmLabel="Delete"
  confirmVariant="danger"
  cancelLabel="Cancel"
  onConfirm={handleDelete}
  onCancel={onClose}
  showIcon={true}
  iconType="warning"
/>

// Good: composable
<Modal>
  <ModalHeader><WarningIcon />Confirm Delete</ModalHeader>
  <ModalBody>Are you sure you want to delete this item?</ModalBody>
  <ModalFooter>
    <Button variant="ghost" onClick={onClose}>Cancel</Button>
    <Button variant="danger" onClick={handleDelete}>Delete</Button>
  </ModalFooter>
</Modal>
```

### Props That Age Well

```tsx
// Brittle: caller controls visual representation
<Button color="red" />

// Stable: caller expresses intent, component decides appearance
<Button variant="danger" />
```

## All States Must Exist

This is the most common failure mode in AI-generated UI. Every data-driven component has states beyond the happy path. All of them must be implemented.

```
Every data-driven component needs:
  loading   → skeleton (not spinner for content areas)
  empty     → purposeful empty state with a call to action
  error     → specific message + recovery action
  populated → the intended working state
```

### Loading

```tsx
// Bad: blank screen
function TaskList() {
  const { data } = useTasks();
  if (!data) return null;
  return <ul>{data.map(...)}</ul>;
}

// Good: skeleton preserves layout
function TaskList() {
  const { data, isLoading, error, refetch } = useTasks();

  if (isLoading) return <TaskListSkeleton count={3} />;
  if (error) return <TaskListError error={error} onRetry={refetch} />;
  if (!data?.length) return <TaskListEmpty onAdd={onCreate} />;
  return <ul role="list">{data.map(t => <TaskItem key={t.id} task={t} />)}</ul>;
}

function TaskListSkeleton({ count }: { count: number }) {
  return (
    <ul aria-busy="true" aria-label="Loading tasks" className="space-y-2">
      {Array.from({ length: count }).map((_, i) => (
        <li key={i} className="h-12 animate-pulse rounded-md bg-muted" />
      ))}
    </ul>
  );
}
```

### Empty States

Empty states are features. They tell the user what the space is for and what to do next.

```tsx
// Bad
if (items.length === 0) return <div />;

// Good
if (items.length === 0) {
  return (
    <div className="flex flex-col items-center gap-4 py-16 text-center">
      <InboxIcon className="h-12 w-12 text-muted" aria-hidden="true" />
      <div>
        <p className="font-medium">No tasks yet</p>
        <p className="text-sm text-muted">Create your first task to get started.</p>
      </div>
      <Button onClick={onCreateTask}>Create Task</Button>
    </div>
  );
}
```

### Error States

```tsx
// Bad
if (error) return <p>Something went wrong.</p>;

// Good
if (error) {
  return (
    <div role="alert" className="rounded-lg border border-destructive/30 bg-destructive/10 p-4">
      <p className="font-medium text-destructive">Failed to load tasks</p>
      <p className="mt-1 text-sm text-muted">{error.message}</p>
      <Button variant="outline" size="sm" className="mt-3" onClick={refetch}>
        Try again
      </Button>
    </div>
  );
}
```

## Interaction Design

### Hover and Focus

Every interactive element must have a visible hover state and a visible focus state. These are not optional.

```css
/* Bad: removes focus with no replacement */
button:focus { outline: none; }

/* Good: replace browser default with styled equivalent */
button:focus-visible {
  outline: 2px solid var(--color-ring);
  outline-offset: 2px;
}

/* Good: hover communicates affordance */
.card:hover {
  box-shadow: 0 4px 12px rgb(0 0 0 / 0.08);
  transform: translateY(-1px);
  transition: box-shadow 150ms ease, transform 150ms ease;
}
```

### Touch Targets

Minimum 44×44px for all interactive elements:

```css
.icon-button {
  display: flex;
  align-items: center;
  justify-content: center;
  min-width: 44px;
  min-height: 44px;
}
```

### Motion

```
Micro-interactions (hover, toggle):    100–150ms
Appearing / disappearing elements:     200–250ms
Page transitions:                      300–400ms
Never:                                 > 500ms for repeated interactions
```

Never use `transition: all`. Animate only cheap composited properties:

```css
/* Bad */
.card { transition: all 0.3s ease; }

/* Good */
.card { transition: box-shadow 150ms ease, opacity 150ms ease; }
```

Always respect `prefers-reduced-motion`:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

### Action Feedback

```
< 16ms    Visual response (hover, active) — CSS, synchronous
< 100ms   Optimistic UI update — before server confirms
> 100ms   Show loading indicator
> 10s     Show timeout / retry prompt
```

## Accessibility (WCAG 2.1 AA)

### Semantic HTML First

```html
<!-- Bad: div soup -->
<div class="btn" onclick="submit()">Submit</div>
<div class="heading">Title</div>

<!-- Good: semantic HTML -->
<button type="submit">Submit</button>
<h2>Title</h2>
```

Reach for ARIA only when HTML has no appropriate element.

### Keyboard Navigation

Tab through every interactive element. Verify:

1. All interactive elements receive focus in logical order
2. Focus is never lost or sent to a void
3. Modals trap focus inside until closed
4. Focus returns to the trigger when a modal or popover closes

```tsx
function Dialog({ isOpen, onClose, triggerRef }: DialogProps) {
  const firstFocusableRef = useRef<HTMLButtonElement>(null);

  useEffect(() => { if (isOpen) firstFocusableRef.current?.focus(); }, [isOpen]);
  useEffect(() => { if (!isOpen) triggerRef.current?.focus(); }, [isOpen, triggerRef]);

  return (
    <dialog
      open={isOpen}
      onKeyDown={e => e.key === 'Escape' && onClose()}
      aria-modal="true"
      aria-labelledby="dialog-title"
    >
      <h2 id="dialog-title">Confirm action</h2>
      <button ref={firstFocusableRef} onClick={onClose}>Cancel</button>
      <button onClick={onConfirm}>Confirm</button>
    </dialog>
  );
}
```

### ARIA Labels

```html
<button aria-label="Close dialog"><XIcon /></button>
<input aria-label="Search" type="search" />
<nav aria-label="Main navigation">...</nav>
```

### Live Regions

```tsx
<div aria-live="polite" aria-atomic="true">{statusMessage}</div>
<div role="alert">{errorMessage}</div>
```

## Responsive Design

Mobile-first. Write the smallest viewport first, expand with breakpoints:

```css
.grid {
  display: grid;
  grid-template-columns: 1fr;
}
@media (min-width: 640px)  { .grid { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 1024px) { .grid { grid-template-columns: repeat(3, 1fr); } }
```

Test at: 320px, 375px, 768px, 1024px, 1280px, 1440px.

Always test with content longer than you expect — long names, wrapped error messages, empty states where CTA text wraps.

## Human Copy and Content

AI-generated interfaces have a recognizable writing style. Eliminate it entirely.

### Over-Explanation

Say the thing. Do not explain that you are about to say the thing:

| AI Default | Human Version |
|---|---|
| "Welcome to your dashboard! Here you can see an overview of all your important metrics and data." | "Your dashboard" |
| "Click the button below to get started with creating your first project." | "Create your first project" |
| "No items have been added yet. You can add items by clicking the button above." | "No items yet" + [Add item] |
| "An error has occurred while processing your request. Please try again later." | "Couldn't save — try again" |
| "Are you sure you want to permanently delete this item? This action cannot be undone." | "Delete this project? This can't be undone." |

### Emoji

```
Allowed:
  One emoji in a headline where personality is intentional
  Status indicators where emoji is an established convention

Never:
  Emoji on every list item or heading
  Emoji in error messages
  Emoji in form labels or placeholders
  Multiple emoji in one sentence
  ✨ on AI features, 🎉 on success states
```

Test: remove the emoji. If the sentence loses nothing, the emoji added nothing.

### Generic AI Phrases

Never use: "seamlessly", "unlock the power of", "take it to the next level", "robust", "leverage", "cutting-edge", "revolutionize".

State what the thing actually does.

### CTA Labels

```
// Bad
"Get Started"
"Learn More"
"Click Here"

// Good
"Create project"
"Connect account"
"View your tasks"
```

### Placeholder Text

```html
<!-- Bad: describes the field -->
<input placeholder="Enter your email address" />
<input placeholder="Type your message here..." />

<!-- Good: shows a real example -->
<input placeholder="you@company.com" />
<input placeholder="What's on your mind?" />
```

### Error Messages

Specific, honest, with a recovery path. Never corporate passive voice:

```
// Bad
"An unexpected error has occurred. We're sorry for the inconvenience."

// Good
"Couldn't connect to the server. Check your connection and try again."
[Try again]  [Contact support]
```

### Empty States

Short and action-oriented. Never a paragraph:

```
// Bad
"It looks like you haven't received any messages yet. Messages from your
team will appear here once they start reaching out to you."

// Good
"No messages"
[Invite your team]
```

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "Accessibility can be added later" | Focus management and semantics cannot be retrofitted without rewriting components. Cost multiplies 5–10× after launch. |
| "The design isn't final, I'll style it properly then" | Unstyled UI is what reviewers and stakeholders see. It sets expectations. Use the design system from day one. |
| "I only need the happy path for now" | Loading, empty, and error are the first states every new user encounters — before they ever see data. |
| "The hover state is implicit" | Users learn what is clickable by what reacts to them. Hover states teach them. |
| "This is just a prototype" | Prototypes become production. Gaps in prototypes become bugs in production. |
| "Emoji makes it feel friendly" | Emoji on every item signals AI generation. One intentional emoji beats ten decorative ones. |
| "Users need the explanation to understand" | Over-explanation signals distrust. If the UI requires paragraphs, the UI is wrong — not the copy. |
| "The error message is fine, users will figure it out" | "Something went wrong" tells the user nothing and helps them do nothing. |

## Red Flags

- Blank screen or `null` return during loading
- Generic "Something went wrong" with no recovery action
- Missing hover or focus states on interactive elements
- `outline: none` with no replacement
- Spacing values not on the project's scale
- `<div onClick>` instead of `<button>` or `<a>`
- Heading elements used for visual size, not structure
- Color as the sole differentiator between states
- `transition: all` anywhere
- Touch targets under 44px
- Emoji on every heading, list item, or section
- Copy that explains what the user is about to do instead of letting them do it
- ✨ or 🎉 on AI features or success states
- Empty state copy longer than two short sentences
- Error messages that don't say what failed or what to do next
- CTAs labeled "Get Started" or "Learn More" with no differentiation
- Placeholder text that describes the field instead of showing an example

## Verification

After completing any UI task, confirm:

- [ ] Renders without console errors or warnings
- [ ] Visual QA: spacing on scale, typography semantic, color contrast passing
- [ ] All states implemented: loading (skeleton), empty (purposeful), error (with recovery), populated
- [ ] All interactive elements keyboard accessible — Tab through the full page
- [ ] Focus states visible on all interactive elements
- [ ] Screen reader announces structure and dynamic changes correctly
- [ ] Tested at 320px, 768px, 1280px viewports
- [ ] Motion respects `prefers-reduced-motion`
- [ ] No `outline: none` without a replacement focus style
- [ ] Touch targets 44×44px minimum
- [ ] No accessibility warnings from axe-core or DevTools
- [ ] Copy is direct — no over-explanation, no AI generic phrases
- [ ] Emoji used intentionally (0–1 per section), not decoratively
- [ ] Error messages say what failed and what to do next
- [ ] Empty states are short and include a call to action
- [ ] CTA labels name the action, not just "Get Started"
- [ ] Placeholder text shows an example, not a description
